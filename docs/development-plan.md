# План технических доработок Coinsa

Зафиксирован по итогам аудита и решений пользователя от 18.11.2026.
Предложения ниже не означают разрешения на их реализацию. Перед работой нужно
перепроверить текущий код и согласовать существенные изменения поведения.

## Оптимизация аналитики

Статус: отложено, требуется отдельная задача. Измерений производительности пока нет;
основание для предложений — повторные обходы и создание промежуточных коллекций.

Основные файлы:

- `Coinsa/Coinsa/Features/EventAnalytics/Presentation/ViewModels/EventAnalyticsViewModel.swift`.
- `Coinsa/Coinsa/Features/EventAnalytics/Presentation/Models/EventExpenseChartTimeline.swift`.
- `Coinsa/Coinsa/Features/EventAnalytics/Presentation/Components/EventDailyExpenseChart.swift`.
- `Coinsa/Coinsa/Features/EventAnalytics/Presentation/ViewModels/EventSubcategoryAnalyticsViewModel.swift`.

План:

1. Измерить подготовку аналитики на синтетических поездках с тысячами трат и длинными
   промежутками между ними. Разделить время агрегации, построения шкалы и отображения.
2. Готовить дневные суммы, максимум, итоги категорий и шкалу согласованным расчетом.
   Сейчас вычисляемые свойства повторяют группировку и поиск максимума.
3. Строить сжатые пустые промежутки по расстояниям между датами, сохраняя нынешние
   границы графика и правила сжатия. Не создавать сначала запись каждого пустого дня.
4. Заменить линейный поиск точки для каждой подписи оси обращением по позиции.
5. Проверить повторные группировки подкатегорий и использование уже подготовленных данных.

Не кешировать результат без определения условий обновления. Изменение суммы, даты,
категории, валютного контекста, связей, добавление и удаление трат, включая изменения
после синхронизации, должны обновлять все связанные итоги и списки.

Проверки: согласованность общих, дневных и категорийных сумм до форматирования;
пустые данные; один день; траты вне дат поездки; длинные промежутки; изменение траты
во вложенном экране и возврат в аналитику. Модели SwiftData не передавать между
задачами без корректной изоляции; при доказанной необходимости фонового расчета
передавать только отдельные значения.

## Рефакторинг работы с курсами

Статус: отложено, требуется отдельная задача. Текущие формулы и согласованное
поведение смены валюты должны сохраняться.

Основные файлы:

- `Coinsa/Coinsa/Core/Domain/ExchangeRates/`.
- `Coinsa/Coinsa/Core/Domain/CurrencyConverter/CurrencyConverter.swift`.
- `Coinsa/Coinsa/Core/Domain/Currency/Managers/AmountManager.swift`.
- `Coinsa/Coinsa/Features/Today/Presentation/ViewModels/TodayViewModel.swift`.
- ViewModels редакторов траты, локации и конвертера.

План:

1. Согласовать единое представление результата загрузки: валютная пара, курс,
   источник и время обновления. Отдельно учитывать сохраненный курс траты,
   ручной ввод и справочный сетевой курс.
2. Рассмотреть общий кеш по валютной паре и объединение одновременных одинаковых
   запросов. Учесть время данных провайдера, принудительное обновление и работу без сети.
3. Проверить владение запросами, отмену и устаревшие ответы. Отмена одного потребителя
   общего запроса не должна неожиданно отменять загрузку для остальных.
4. Проверять HTTP-ответ и корректность ответа провайдера; изменение политики обработки
   невалидных чисел согласовать отдельно, поскольку сейчас оно отложено пользователем.
5. Решить, как показывать дату и источник курса, не смешивая их с историческим курсом траты.

Сохранение прежнего положительного курса после смены пары до успешной загрузки
нового, включая ошибку сети, пользователь считает нормой. Не превращать эту задачу
в обнуление курса или новый запрет сохранения без отдельного согласования.
Исторические суммы и курсы автоматически не обновлять.

## Внедрение зависимостей

Статус: отложено, требуется отдельная задача. Начать с существующего
`ExchangeRateService` и передачи `ExchangeRateProvider` через инициализаторы.
Новые универсальные контейнеры зависимостей и слой общих репозиториев не нужны.

Приоритетные места: `ExpenseEditViewModel`, `LocationEditViewModel`,
`CurrencyConverterViewModel`; ориентир — уже поддерживающий передачу провайдера
`TodayViewModel`.

Сохранить удобные рабочие инициализаторы с текущими зависимостями по умолчанию.
Для проверок и превью разрешить передавать локальные заглушки без сети.
Перед расширением внедрения на геолокацию или часы определить конкретный сценарий,
который невозможно надежно проверить с нынешним API.

Проверки заглушками: успех, ошибка, отмена, быстрые последовательные смены валют,
ответы в обратном порядке, обновление курса при выбранной стороне суммы,
повторное открытие редактора и отключенная автоматическая загрузка.

## Решения по замечаниям аудита

- Защита валюты локации при наличии трат, дробные смещения GMT и счетчик получателей
  бюджета доработаны в задаче от 18.11.2026.
- Обработка вставки суммы с другим десятичным разделителем не меняется по решению пользователя.
- Дополнительная защита от NaN/Infinity и privacy manifest пока отложены.
- Защита записи при временно отсутствующих родителях пока не реализуется. Само
  ожидание загрузки связей нормально; риск представляет сохранение с подстановкой
  валюты по умолчанию. Возможная отдельная задача — проверять необходимых родителей
  в редакторе и перед записью, сохранять черновик и позволять повторить операцию.
