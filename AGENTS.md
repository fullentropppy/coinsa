# Правила работы AI-агентов в Coinsa

Эти инструкции действуют для всего репозитория. Выполняй только работу в рамках задачи пользователя.
Явное разрешение на конкретное действие в текущей задаче считается согласованием; не запрашивай его повторно.

Перед правками уточняй существенные неоднозначности, влияющие на поведение, данные или объём задачи. При их наличии дождись ответа до зависимых изменений; очевидные детали реализации решай самостоятельно.

## Контекст проекта

- Coinsa — iPhone-приложение для учёта расходов в путешествиях, бюджетов, валют и аналитики.
- Основные технологии: SwiftUI, Observation, SwiftData, CloudKit, Swift Charts, MapKit, CoreLocation и UIKit.
- Курсы загружаются из Hexarate через `URLSession`; сторонних пакетных зависимостей сейчас нет.
- Минимальная версия — iOS 26.0. Проверяй доступность новых API относительно deployment target.
- Проект: `Coinsa/Coinsa.xcodeproj`; единственный application target — `Coinsa`.
- Общие схемы: `Coinsa Debug` использует Debug для Run и Archive; `Coinsa` — Release для Run и Archive.
- Для разработки предпочитай `Coinsa Debug`. Обе схемы сейчас запускают приложение без выбранного LLDB.
- В проекте задан Swift language mode 5.0, default actor isolation `MainActor` и Approachable Concurrency.
- При расхождении README и исходников проверяй факты по коду и настройкам проекта; сообщай о расхождении.

## Каталоги и ответственность слоёв

Каталоги исходников ниже указаны относительно `Coinsa/Coinsa/`; `docs/` находится в корне репозитория.

| `SharedUI/` | Общие компоненты, числовой ввод, форматирование и представления доменных типов |

| `Previews/` | Генераторы примеров и контейнеры для SwiftUI previews |

## Архитектура и изменения кода

- Следуй существующей feature-based организации и MVVM; размещай изменения рядом с соответствующей функцией.
- Views отвечают за отображение, навигацию, bindings и получение окружения; не переноси в них бизнес-расчёты.
- ViewModels управляют состоянием формы, валидацией и действиями; Domain содержит переиспользуемые правила и вычисления.
- Чтение через `@Query` и связи моделей допустимо во Views; изменения постоянных моделей проводи через Repositories.
- Сохраняй черновое состояние редакторов до сохранения и существующее определение изменений через snapshots.
- Состояние редакторов реализовано через `@Observable`-классы и `@State`; простые ViewModels могут быть структурами.
- Настройки передаются через Environment как `AppSettingsStore` и хранятся в `UserDefaults`; haptics — через Environment key.
- Уважай изоляцию `MainActor`; не передавай `ModelContext` и связанные модели между задачами без корректной изоляции.
- Предпочитай простое решение в существующих типах. Вводи протоколы, слои и абстракции только для конкретной потребности задачи.
- Не вводи новый архитектурный паттерн и не проводи несвязанный рефакторинг, переименования или массовое форматирование.
- Перед существенными изменениями изучи вызывающий код, связанные модели, вычисления, сохранение и существующие previews.
- Для неоднозначного архитектурного решения кратко объясни подход, существенную альтернативу и причину выбора.

## Стиль и локализация

- Следуй соседним файлам: Swift naming conventions, отступы, `MARK`, расширения по ответственности и русские Doc Comments.
- Не добавляй комментарии внутри тел функций и у свойств по собственной инициативе. Добавляй их только по явной просьбе пользователя или для сохранения уже существующего стиля комментирования в изменяемом коде.
- В добавляемых комментариях объясняй причины и нетривиальные ограничения; поддерживай существующие комментарии изменяемого кода актуальными.
- Пользовательские строки добавляй в `Resources/Localizable.xcstrings` для `en` и `ru`. Формируй смысловые ключи с точками по образцу соседних (`settings.…`, `amount.…`); во Views используй сгенерированные типизированные обращения (`Text(.settings…)`), а не строковые литералы или ручные дубликаты ключей.
- Тексты системных запросов доступа локализуй в `Resources/InfoPlist.xcstrings` для `en` и `ru`, используя системные ключи Info.plist. Резервные значения usage descriptions в настройках Debug и Release задавай на английском.
- UI-представления доменных типов размещай в UIExtensions или SharedUI по существующему образцу.
- Не дублируй форматирование денег, дат и валют: сначала проверь существующие Formatters и общие компоненты.
- Не добавляй зависимости и инструменты, не требуемые задачей; объясняй необходимость новых зависимостей.

## SwiftData, CloudKit и совместимость

- Считай существующие пользовательские данные обязательными к сохранению, даже если локально приложение установлено впервые.
- Текущая схема: `Trip`, `Location`, `Expense`; `ModelContainer` создаётся в `App/Main/CoinsaApp.swift`.
- Связи `Trip → Location → Expense` optional; удаление родителя каскадно удаляет дочерние записи.
- Не меняй persisted-поля, их имена, типы, defaults, связи, delete rules, raw values, ключи UserDefaults или структуру хранения без анализа совместимости и явного согласования.
- До такого согласования опиши влияние на старые локальные данные, CloudKit, разные версии приложения и способ проверки миграции.
- В проекте пока нет `VersionedSchema` и `SchemaMigrationPlan`; не считай автоматическую миграцию гарантией совместимости.
- TODO о переименовании `baseCurrencyCode`, `baseAmount`, `rateLocationToBase`, `rateExpenseToBase` не разрешают менять схему.
- Используй существующие вычисляемые свойства `homeAmount`, `rateExpenseToHome` и `rateLocationToHome` без переименования полей хранения.
- Учитывай ограничения CloudKit: optional-связи, отсутствие поддержки unique constraints и добавочный характер production-схемы.
- Обрабатывай временно отсутствующих родителей и неизвестные raw values; не добавляй принудительные unwraps для связей.
- Не меняй bundle IDs, CloudKit containers, entitlements и серверную схему в рамках обычного рефакторинга.
- Debug использует `ru.dgritsenko.Coinsa.debug` и `iCloud.ru.dgritsenko.Coinsa.debug`; Release — идентификаторы без `.debug`.
- Выбор контейнера находится в `Core/Configs/AppInfo.swift`; он должен оставаться согласованным с build settings и entitlements.
- Отдельный Debug-контейнер не означает отключённую синхронизацию и не подтверждает окружение CloudKit Development/Production.
- Без разрешения не выполняй сброс, массовое удаление, очистку stores, переустановку с потерей данных или изменение серверных записей.
- `DemoDataService.loadDemoData()` сначала удаляет и сохраняет старые данные; считай его разрушительной операцией.
- Не используй реальные пользовательские данные, их копии или личный iCloud для тестирования; не помещай их в логи и fixtures.

## Деньги, валюты, даты и часовые пояса

- Бюджет `Location.budget` и сумма `Expense.baseAmount` хранятся в домашней валюте поездки; сейчас используется `Double`.
- Не меняй тип хранения, точность или округление без анализа влияния на сохранённые суммы и согласования изменения хранения.
- Различай `.home`, `.location`, `.expense`; проверяй направление курса и соответствие курса текущей валютной паре.
- Используй `ExpenseCalculationContext`, `CurrencyConverter`, `AmountManager` и существующую логику расчётов вместо дублирования формул.
- Учитывай `ExchangeRateMode` и корректировку курса: в расчётах траты она применяется для оплаты картой в иностранной валюте.
- Проверяй нулевые, отрицательные и неконечные значения (NaN/Infinity), деление на ноль, ошибку сети и смену валюты во время загрузки.
- Не подставляй старый курс для новой пары и не обновляй исторические суммы текущим курсом без явного требования задачи.
- `PlainDate` хранит календарную дату как UTC 00:00; `CivilDateTime` — гражданские компоненты даты и времени в UTC-представлении.
- Это представления календарных компонентов; фактический момент траты хранится отдельно в `actualDate`, пояс — в `timeZoneID`.
- Используй существующие преобразования; учитывай смену пояса, DST, полночь и включённые границы диапазонов дат.
- При редактировании траты сохраняй исходные `timeZoneID` и `actualDate`, если итоговые гражданские дата и время не изменились, включая возврат к исходному значению. При их изменении `ExpenseRepository` пересчитывает момент и записывает текущий пояс.

## Инструменты и безопасное выполнение

- Для навигации по проекту, диагностики и разрешённых сборок используй подключённый Xcode MCP, когда это целесообразно.
- Перед действиями через MCP проверь выбранные project, scheme и destination; не полагайся на текущий выбор Xcode.
- Если MCP недоступен, используй доступные локальные средства; сообщи об ограничении и не меняй интеграции без задачи на настройку.
- Перед CLI-сборкой проверь путь полного Xcode через `xcode-select` или `DEVELOPER_DIR`; не меняй системный выбор молча.
- Не запускай приложение, тесты и другие тестовые операции на физическом iPhone без явного разрешения.
- Для автоматических проверок предпочитай изолированный iOS Simulator с синтетическими данными и без личного iCloud.
- Проверки хранения проводи в отдельном in-memory или временном store с отключённым CloudKit и отдельным UserDefaults suite.
- Проверку синхронизации проводи отдельно, с тестовыми данными и аккаунтом, по согласованному сценарию.
- Не считай previews полностью изолированными автоматически: проверяй обращения к сети, UserDefaults и другим внешним зависимостям.
- Не устанавливай и не обновляй SDK, зависимости и инструменты, не меняй signing и настройки Xcode без соответствующей задачи.
- Указанные пользователем ограничения на сборку, запуск, тесты и запись файлов имеют приоритет над обычным процессом проверки.

## Проверки и отчёт о результате

- Автоматизированных тестов и test targets пока нет; наличие `TestAction` в схемах не означает наличие тестов.
- Не придумывай команды проверок. Выбирай проверки по фактическим инструментам, targets и ограничениям текущей задачи.
- Для изменений логики предлагай или добавляй уместные тесты в рамках задачи; не создавай тестовую инфраструктуру ради правки текста.
- Приоритетные сценарии: ошибки сохранения, миграции, каскадное удаление, optional-связи, валютные пары, округление и часовые пояса.
- Проверяй обработку ошибок и пограничные случаи; в async-коде — отмену, повторные запросы, устаревшие ответы и жизненный цикл объектов.
- Существующее `try? context.save()` не является образцом обработки ошибок; при работе с записью проверяй, как ошибка попадёт в UI.
- Перед завершением просмотри итоговый diff: только изменения по задаче, без случайных файлов и настроек.
- В итоговом ответе перечисли изменённые файлы, выполненные проверки и их результаты, оставшиеся риски и ограничения.
- Если сборка или тесты не выполнялись, прямо укажи это; чтение кода и проверка diff не подтверждают успешную сборку.
