# Правила работы AI-агентов в Coinsa

Эти инструкции действуют для всего репозитория. Выполняй только работу в рамках задачи пользователя.
Явное разрешение на конкретное действие в текущей задаче считается согласованием; не запрашивай его повторно.

Перед правками уточняй существенные неоднозначности, влияющие на поведение, данные или объём задачи. При их наличии дождись ответа до зависимых изменений; очевидные детали реализации решай самостоятельно.

## Контекст проекта

- Coinsa — iPhone-приложение для учёта расходов в путешествиях, бюджетов, валют и аналитики.
- Основные технологии: SwiftUI, Observation, SwiftData, CloudKit, Swift Charts, MapKit, CoreLocation и UIKit.
- Курсы загружаются из Hexarate через `URLSession`; в iOS-приложении сторонних пакетных зависимостей сейчас нет.
- Минимальная версия — iOS 26.0. Проверяй доступность новых API относительно deployment target.
- Проект: `Coinsa/Coinsa.xcodeproj`; единственный application target — `Coinsa`.
- Общие схемы: `Coinsa Debug` использует Debug для Run и Archive; `Coinsa` — Release для Run и Archive.
- Для разработки предпочитай `Coinsa Debug`. Обе схемы сейчас запускают приложение без выбранного LLDB.
- В проекте задан Swift language mode 5.0, default actor isolation `MainActor` и Approachable Concurrency.
- При расхождении README и исходников проверяй факты по коду и настройкам проекта; сообщай о расхождении.
- Версию и номер сборки приложения получай через `AppInfo.version` и `AppInfo.build`.

## Каталоги и ответственность слоёв

Каталоги исходников ниже указаны относительно `Coinsa/Coinsa/`; `docs/` и `backend/` находятся в корне репозитория.

| Каталог | Ответственность |
| --- | --- |
| `App/` | Точка входа, `ModelContainer`, корневые Views и вкладки |
| `Features/` | Trip, Location, Expense, Today, CurrencyConverter, EventSummary, EventAnalytics, Settings |
| `Features/*/Presentation/` | Views, ViewModels, компоненты и UIExtensions конкретной функции |
| `Features/*/Domain/` | Модели, правила и вычисления конкретной функции |
| `Features/*/Data/` | Репозитории, Stores и Managers для хранения данных |
| `Core/` | Общие доменные типы, валюты, даты, координаты, сервисы курсов и утилиты |
| `SharedUI/` | Общие компоненты, числовой ввод, форматирование и представления доменных типов |
| `Infrastructure/` | Haptics и debug-сервис управления демоданными |
| `Previews/` | `Data/` — синтетические модели и наборы примеров, общие с демоданными; `Support/` — окружение и построитель превью; `Scenarios/` — подготовка отдельных экранов |

## API проверки обновлений

- Приложение получает публичный JSON с Cloudflare через `URLSession`. Адрес API, интервал проверки и таймаут заданы в `Core/Configs/AppUpdateConfig.swift`; логика находится в `Core/Domain/AppUpdate/`, подключение к жизненному циклу — в `App/Root/RootContainerView.swift`.
- Данные версии находятся в `backend/public/ios/testflight.json`. Поле `notificationEnabled` разрешает показ уведомления о более новой версии и сборке; отключение применяется после следующей успешной проверки API. Публичную ссылку-приглашение TestFlight в JSON не добавляй.
- Для Git используются корневой `.gitignore` и `backend/.gitignore`; для исключения файлов из публикации Cloudflare — `backend/public/.assetsignore`. Правила Git не заменяют исключения статических файлов сервиса.
- Публикация сервиса выполняется отдельно от сборки iOS командой `npx wrangler deploy` из `backend/`. Для сборки iOS-приложения Node.js и доступ к аккаунту Cloudflare не требуются. Ошибка API не блокирует работу приложения; в SwiftUI previews проверка отключена.

## Архитектура и изменения кода

- Следуй существующей feature-based организации и MVVM; размещай изменения рядом с соответствующей функцией.
- Views отвечают за отображение, навигацию, bindings и получение окружения; не переноси в них бизнес-расчёты.
- ViewModels управляют состоянием формы, валидацией и действиями; Domain содержит переиспользуемые правила и вычисления.
- Чтение через `@Query` и связи моделей допустимо во Views; изменения постоянных моделей проводи через Repositories.
- Сохраняй черновое состояние редакторов до сохранения и существующее определение изменений через snapshots.
- Состояние редакторов реализовано через `@Observable`-классы и `@State`; простые ViewModels могут быть структурами.
- Настройки передаются через Environment как `AppSettingsStore` и хранятся в `UserDefaults`; haptics — через Environment key.
- Уважай изоляцию `MainActor`; не передавай `ModelContext` и связанные модели между задачами без корректной изоляции.
- Предпочитай простое решение в существующих типах. Вводи протоколы, слои и абстракции только для конкретной потребности задачи.
- Не вводи новый архитектурный паттерн и не проводи несвязанный рефакторинг, переименования или массовое форматирование.
- Перед существенными изменениями изучи вызывающий код, связанные модели, вычисления, сохранение и существующие previews.
- Для неоднозначного архитектурного решения кратко объясни подход, существенную альтернативу и причину выбора.

## Разделение экранов редактирования

- Редакторы Expense, Location и Trip разделены на вход, контейнер и форму по правилам ниже. При дальнейшей декомпозиции выделяй 2–3 файла по ответственности, а не по формальному числу строк. Само наличие этих правил не разрешает рефакторинг других экранов вне текущей задачи.
- `<Entity>EditorView` в `Presentation/Views/` — единый вход в создание и редактирование: сохраняет внешние инициализаторы и обрабатывает недоступность исходных данных. `<Entity>EditorContainerView` там же владеет состоянием интерфейса, фокусом, задачами, навигацией, тулбаром, предупреждениями и действиями. `<Entity>FormView` в `Presentation/Components/` отображает `Form`, секции и bindings полей и вызывает переданные действия.
- Для Location используются `LocationEditorView`, `LocationEditorContainerView`, `LocationFormView`; для Trip — `TripEditorView`, `TripEditorContainerView`, `TripFormView`. Слово `Editor` обозначает оба режима, а `Container` и `Form` — разные ответственности; не оставляй параллельно старые и новые имена одного компонента. При согласованном переименовании обновляй все обращения, имена файлов и превью.
- Не выделяй пустую оболочку только ради трех файлов: если отдельная ответственность отсутствует, достаточно двух компонентов. Не заменяй декомпозицию массовым расширением доступа к `private`-состоянию ради extensions в разных файлах.
- Сохраняй один экземпляр ViewModel и его жизненный цикл: вход редактора хранит optional-черновик через `@State` для обработки недоступности данных и передаёт тот же экземпляр контейнеру. Контейнер хранит его через `@State`, поля получают его через `@Bindable`. Не создавай ViewModel заново в `body`, секциях или дочерних компонентах и не копируй черновик в независимое состояние.
- `@FocusState`, выбранные режимы ввода, флаги сохранения и дескрипторы асинхронных задач оставляй у контейнера редактора. Передавай в поля проекции фокуса, необходимые значения и callbacks. Подключай `.keyboardInputBar` один раз к контейнеру редактора; сохраняй завершение ввода, очистку активного поля и обновление отображаемой суммы при переключении валюты.
- Оставляй сохранение, удаление, отмену, открытие дополнительных экранов и обработку ошибок в контейнере редактора с существующей ViewModel и Repository. Поля вызывают переданные действия; не заводи в них второй Repository, набор задач или собственную копию `AppSettingsStore`.
- Закрывай редактор только после успешного сохранения или удаления; `onDelete` вызывай только после успешной записи удаления. При ошибке сохраняй черновик и показывай сообщение до подтверждения пользователем; оставляй возможность повторить операцию.
- Перенос секций не должен менять пользовательские строки, порядок секций, bindings, haptics, snapshots, валидацию, подтверждения, применение курсов и обработку отмены задач. Особенности бюджета и валют Location, дат и домашней валюты Trip сохраняй по их текущему коду; не копируй расчеты Expense в другие функции.
- В каждом новом файле View или компонента формы оставляй `// MARK: - Превью` и отдельные `#Preview("Editing")` / `#Preview("Creating")` по образцу исходного редактора. Используй `PreviewGenerator`; общую подготовку нескольких превью размещай в `Previews/`. Для полей добавляй локальные preview-состояния фокуса и переключателей, не меняя рабочий API ради превью.
- Подключай нужные Environment-зависимости превью явно. Для интерактивной записи используй отдельный in-memory контейнер с `cloudKitDatabase: .none`, отдельный UserDefaults suite и отключенную автоматическую загрузку курсов и геолокацию. Не объявляй превью полностью изолированным, если его ручные действия еще обращаются к внешним сервисам.
- Общие контейнеры и настройки превью создавай через `Previews/Support/PreviewEnvironment.swift`; удерживай окружение через `@Previewable @State`. Данные генерируй с одной опорной датой, календарную арифметику в формате хранения выполняй в UTC, а `actualDate` синтетической траты вычисляй в её `timeZoneID`. `DemoDataService` использует генератор напрямую, без окружения превью.
- После разделения сравни перенесенные обработчики и bindings с исходником, проверь новые файлы в сборке `Coinsa Debug` для iOS Simulator без запуска и итоговый diff. Визуальную проверку оставляй пользователю, если он явно не поручил её агенту; в отчете различай выполненные проверки.

## Стиль и локализация

- Следуй соседним файлам: Swift naming conventions, отступы, `MARK`, расширения по ответственности и русские Doc Comments.
- Не добавляй комментарии внутри тел функций и у свойств по собственной инициативе. Добавляй их только по явной просьбе пользователя или для сохранения уже существующего стиля комментирования в изменяемом коде. Исключение — константы оформления: для них Doc Comments обязательны по правилам ниже.
- В добавляемых комментариях объясняй причины и нетривиальные ограничения; поддерживай существующие комментарии изменяемого кода актуальными.
- Каждый явно объявленный `init`, включая приватные и инициализаторы вложенных типов, должен иметь русский Doc Comment о назначении и существенных особенностях инициализации. Кратко описывай каждый параметр через `- Parameter` или `- Parameters`; для `init` без параметров достаточно описания назначения.
- В каждом новом файле исходного кода добавляй шапку с именем файла, названием проекта `Coinsa` и строкой `Created by Daniil Gritsenko on DD.MM.YYYY.`. Подставляй фактическое имя файла с расширением и дату создания: двузначные день и месяц, четырехзначный год. Используй синтаксис комментариев соответствующего формата; для Swift шапка должна выглядеть так:

```swift
//
//  <ИмяФайла>.swift
//  Coinsa
//
//  Created by Daniil Gritsenko on <DD.MM.YYYY>.
//
```

- Пользовательские строки добавляй в `Resources/Localizable.xcstrings` для `en` и `ru`. Формируй смысловые ключи с точками по образцу соседних (`settings.…`, `amount.…`); во Views используй сгенерированные типизированные обращения (`Text(.settings…)`), а не строковые литералы или ручные дубликаты ключей.
- Пока не добавляй accessibility-тексты, атрибуты, модификаторы и связанные с ними локализации без отдельной задачи пользователя.
- Тексты системных запросов доступа локализуй в `Resources/InfoPlist.xcstrings` для `en` и `ru`, используя системные ключи Info.plist. Резервные значения usage descriptions в настройках Debug и Release задавай на английском.
- UI-представления доменных типов размещай в UIExtensions или SharedUI по существующему образцу.
- Не дублируй форматирование денег, дат и валют: сначала проверь существующие Formatters и общие компоненты.
- Не добавляй зависимости и инструменты, не требуемые задачей; объясняй необходимость новых зависимостей.

### Правила локализации и ключей

- Поддерживай одинаковый смысл в `en` и `ru`: условия, ограничения, последствия действий и следующий шаг должны совпадать. Перед изменением подсказки проверяй поведение по коду.
- В русских пользовательских строках используй «е» без диакритики. Сущность Expense всегда называй «трата», во множественном числе — «траты»; не заменяй ее словом «расход».
- Различай локацию поездки (`Location`) и место траты (геопозицию, координаты). Для геопозиции используй пользовательские названия «Место траты» / `Expense location` и ключи `expense.place.*`; `location.*` и `expense.location` относятся к сущности Location. Не называй очистку места траты удалением локации.
- Для добавления сущностей используй «Добавить» / «Добавьте» и `Add`; для повторной попытки — «Повторите попытку.» / `Try again.`. В подсказках предпочитай прямые конструкции: «Валюту можно изменить, если…», «Эти данные можно изменить…».
- В английском используй регистр предложения: заглавная буква в начале, а `trip`, `location`, `expense` в середине — со строчной. Сохраняй регистр имен собственных и аббревиатур (`Coinsa`, `GitHub`, `API`, `EXR`); не меняй утвержденные названия категорий и подкатегорий автоматически.
- Сохраняй согласованные сокращения для компактного интерфейса. Не разворачивай их без отдельной задачи и не меняй короткое название настройки «Доп. бюджет при перерасходе» / `Add’l budget on overspend`; подробное поведение объясняй в подсказке.
- Кнопки и короткие подписи оформляй без точки, полные предложения в сообщениях и подсказках — с точкой, вопросы подтверждения — с вопросительным знаком. Не добавляй ручные переносы строк только для подгонки текста под один размер экрана; сохраняй смысловые абзацы.
- Ошибка должна кратко объяснять, что не удалось, и предлагать доступное действие. Не обещай восстановление после синхронизации и не предлагай отсутствующую команду обновления. В подтверждении удаления указывай также каскадно удаляемые данные.
- Строй смысловые ключи от области к контексту и назначению, разделяя сегменты точками; каждый сегмент пиши в `lowerCamelCase`. Не включай в ключ текст перевода, `Exception` или префикс `is` из имени Boolean-свойства.
- Для ошибок используй `<область>[.<контекст>].error[.<причина>].<title|message>`: например, `trip.storage.error.title`, `trip.storage.error.save.message`, `location.budgetTransfer.error.balanceChanged.message`. `error` обозначает сценарий, `title` и `message` — роль строки; не объединяй причину и тип события в `saveError`.
- Для подтверждений используй парные `.title` / `.message` в одном контексте (`trip.delete.*`, `location.budgetTransfer.confirmation.*`); для результата — `.success.message`, для пустого состояния — `.emptyState.title` / `.emptyState.description`, для недоступности формы — `.editor.unavailable.title` / `.editor.unavailable.message`. Состояние недоступности не обязано находиться в ветке `error`.
- Подписи полей и действий могут находиться непосредственно в смысловом ключе (`expense.amount`, `expense.place.choose`); дополнительные тексты — в `.placeholder` / `.hint`. Заголовки навигации оставляй в `.navigationTitle[.<режим>]`; проверку ввода — в `validation.<поле или сущность.поле>.<причина>`. Общие действия (`add`, `cancel`, `close`, `save`) сохраняй в существующих корневых ключах.
- Не объединяй ключи только из-за одинакового текста: вкладка, заголовок экрана, поле формы и разные доменные понятия могут потребовать разных переводов. При переименовании обновляй каталог и все типизированные обращения одновременно, не оставляй старый ключ как дубликат. Не удаляй потенциально неиспользуемые ключи без проверки всех способов обращения.
- Параметры подстановки называй по смыслу в `lowerCamelCase`; сохраняй одинаковые имена, типы и количество в обоих переводах. Для нескольких параметров явно задавай позиции. Не составляй предложения конкатенацией переведенных фрагментов; единицы измерения также должны учитывать локаль.
- Все переводимые записи должны иметь явные значения `en` и `ru` со статусом `translated`. Непереводимые символы и имена отмечай `shouldTranslate: false`; системные ключи `InfoPlist.xcstrings` не переименовывай, а английские резервные usage descriptions в Debug и Release поддерживай согласованными с каталогом.

## Константы оформления

- Для заливки включенных переключателей `Toggle` всегда используй акцентный цвет через `.tint(.accent)`.
- Имена SF Symbols храни в `SharedUI/Models/AppSymbols.swift`, включая символы для `Label`, вкладок и маркеров SwiftUI/MapKit/UIKit. Соответствие доменной сущности иконке оставляй в существующих UIExtensions; там используй каталог, а не повторяй имена символов строками. Иконки приложения в `Resources/*.icon` и настройках сборки остаются ресурсами Xcode.
- Повторяющееся оформление иконок задавай через `AppIcon` по роли: поля формы, метаданные, служебные элементы ввода и индикаторы пикеров. Для комментариев используй `CommentIcon` с обычным или компактным вариантом. Одинаковый символ в разных ролях не обязан иметь одинаковый размер и цвет; однотипные роли должны использовать общий стиль.
- Повторяющиеся сочетания шрифта и цвета вспомогательного текста задавай через `AppTextStyle` и `.appTextStyle(_:)`. В компонентах с настраиваемыми `font` и `color` используй свойства того же стиля для предопределенных вариантов. Форматирование чисел, денег и дат сохраняй в существующих форматтерах.

## Деньги, валюты, даты и часовые пояса

- Бюджет `Location.budget` и сумма `Expense.baseAmount` хранятся в домашней валюте поездки; сейчас используется `Double`.
- Не меняй тип хранения, точность или округление без анализа влияния на сохранённые суммы и согласования изменения хранения.
- Домашнюю валюту поездки нельзя менять при наличии локаций. Ограничение проверяется в `TripRepository.update` непосредственно перед записью; блокировки пикера недостаточно, поскольку связи могут измениться при синхронизации. При обновлении такой поездки сохраняй исходный `baseCurrencyCode` без перезаписи.
- Валюту локации нельзя менять при наличии трат. Ограничение проверяется в `LocationRepository.update` перед записью; при неизменной валюте сохраняй исходный `locationCurrencyCode` без перезаписи. При отказе редактор восстанавливает сохраненные валюту и курс, сохраняя домашнюю сумму и остальные поля черновика.
- Различай `.home`, `.location`, `.expense`; проверяй направление курса и соответствие курса текущей валютной паре.
- Используй `ExpenseCalculationContext`, `CurrencyConverter`, `AmountManager` и существующую логику расчётов вместо дублирования формул.
- Учитывай `ExchangeRateMode` и корректировку курса: в расчётах траты она применяется для оплаты картой в иностранной валюте.
- Проверяй нулевые, отрицательные и неконечные значения (NaN/Infinity), деление на ноль, ошибку сети и смену валюты во время загрузки.
- `Expense.isExcludedFromDailySpending` по умолчанию выключен. На «Сегодня» такая трата остается в списке, но не входит в дневную сумму и проверку порога перерасхода; ее сумма заранее вычитается перед распределением бюджета по дням. Общие итоги локации и поездки учитывают все траты; при переключении сводки на всю локацию остаток также учитывает все траты.
- По решению пользователя от 18.11.2026 сохранение прежнего положительного курса при смене пары до успешной загрузки нового, в том числе при ошибке сети, считается допустимым текущим поведением. Не меняй его без отдельной задачи. Не обновляй исторические суммы текущим курсом без явного требования задачи.
- `PlainDate` хранит календарную дату как UTC 00:00; `CivilDateTime` — гражданские компоненты даты и времени в UTC-представлении.
- Это представления календарных компонентов; фактический момент траты хранится отдельно в `actualDate`, пояс — в `timeZoneID`.
- Используй существующие преобразования; учитывай смену пояса, DST, полночь и включённые границы диапазонов дат.
- Длительность календарного диапазона считай через `PlainDate.days(from:)` с включением обеих дат. Не вычисляй её через `Calendar.current` для дат в формате хранения UTC: на переходах DST результат может отличаться на день.
- При редактировании траты сохраняй исходные `timeZoneID` и `actualDate`, если итоговые гражданские дата и время не изменились, включая возврат к исходному значению. При их изменении `ExpenseRepository` пересчитывает момент и записывает текущий пояс.
- При копировании траты сохраняй исходные гражданские дату и время, `timeZoneID` и `actualDate`, пока дата черновика не изменена. Копирование выполняется внутри одной поездки; при смене валюты локации обновляй только необходимый курс к ней, сохраняя сумму, валюту траты и курс к домашней валюте. Автоматическая геолокация не должна менять место копии.

## Импорт и экспорт

- Функция находится в `Features/DataTransfer/`, вход — из настроек. Файл `.coinsa` содержит все поездки, локации и траты, без настроек приложения и служебных идентификаторов SwiftData/CloudKit.
- Экспорт использует версию формата 2 с признаком `isExcludedFromDailySpending`. Импорт поддерживает версии 1 и 2; в старых файлах отсутствующий признак считается выключенным.
- Формат версионируется отдельно от приложения. Связи записываются по UUID; календарные дни и гражданские дата/время — строками без пересчета пояса. Метаданные `Date` кодируются стандартным JSON-кодированием Foundation как секунды относительно 01.01.2001 UTC, без округления. Обязательные nullable-ключи должны присутствовать со значением `null`.
- Импорт добавляет отсутствующие UUID, обновляет существующие записи при более позднем или равном `updatedAt` из файла и пропускает старые версии. Сравнивай каждую сущность отдельно, включая дочерние записи пропущенного родителя. Сохраняй `updatedAt` из файла и `createdAt` существующей записи.
- Не удаляй записи, отсутствующие в файле. Ранее удаленная запись из файла добавляется заново; история удалений не хранится. Не переноси существующие записи к другим родителям и не допускай конфликтов валют при объединении.
- Проверяй весь файл и итоговый граф до записи, показывай сводку и повторно проверяй исходный снимок перед подтвержденным сохранением. При изменении данных пересчитывай сводку и запрашивай повторное подтверждение.
- Импорт выполняется через отдельный `ModelContext` с отключенным autosave одной локальной транзакцией с откатом при ошибке. Не используй CRUD-методы редакторов, меняющие даты, курсы или метаданные. При несохраненных изменениях основного контекста откладывай перенос, не сохраняй и не откатывай чужую работу.
- Локальные проверки UUID и транзакция не гарантируют глобальную уникальность и атомарность CloudKit при одновременной работе устройств.

- Не подавляй ошибки записи через `try? context.save()`; при работе с сохранением и удалением проверяй весь путь ошибки от Repository до UI и сохранность черновика при повторной попытке.
- Перед завершением просмотри итоговый diff: только изменения по задаче, без случайных файлов и настроек.
- В итоговом ответе перечисли изменённые файлы, выполненные проверки и их результаты, оставшиеся риски и ограничения.
- Если сборка или тесты не выполнялись, прямо укажи это; чтение кода и проверка diff не подтверждают успешную сборку.

## Актуальность инструкций

неактуальными AGENTS.md и проектные Skills.

Если изменения затрагивают описанные архитектурные
соглашения, инварианты или процедуры, обновляй
соответствующие инструкции в рамках задачи.

Не изменяй инструкции при обычных правках,
не влияющих на их содержание. Не переписывай
документы без необходимости.
